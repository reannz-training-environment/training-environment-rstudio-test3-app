### Emulated GPUs

There is no physical GPU. The [GPU emulator](https://github.com/nesi/training-environment-jupyter-gpu-app)
(v0.5.3) presents NVIDIA cards that `nvidia-smi`, `nvtop`, NVML,
PyTorch's `torch.cuda` and the Slurm emulator all agree on, and enforces their memory
limits, but all computation runs on the CPU. **No timing measured in this
environment means anything about GPU performance**; the session banner, the
connect button and this README all say so, and should keep saying so.

Each session has one GPU, which the learner chooses on the launch form from
`l4`, `a100_40`, `a100`, `h100`, `pro_6000`.

Request a GPU in a batch job as on the cluster, e.g. `#SBATCH --gpus-per-node=l4:1`.
A job that does not ask for a GPU cannot see one, and a job that asks for a
card the node does not have is refused. `sinfo -l` lists the node's cards.
`seff` and `svisit` are NeSI's own, from
[nesi/opt-nesi-bin](https://github.com/nesi/opt-nesi-bin): `svisit <jobid>`
opens a shell inside a running job, where `nvtop` shows its GPU, and `seff`
reports a finished job's GPU memory against the real board's size, as it does
on the cluster, even when the emulated card is smaller.
See the GPU app's README for what the emulator can and cannot teach.

### Environment modules

Lmod is installed, and `module avail`, `module load` and `module spider` work
in terminals, notebooks' terminals and batch jobs.
Each conda package is a module: `module load <name>` puts that package's
commands, and nothing else, on `PATH`. The modulefiles are generated at build
time by `docker/scripts/make-conda-wrappers.py`; `/opt/software/packages.tsv`
lists them.

## Adding the app to the training environment

The cluster pulls the image without credentials, so it must be public. It is
public from the start when the organisation allows public packages and this
repository is public. Otherwise it starts private, and GitHub has no API to
change that: open the
[package settings](https://github.com/orgs/reannz-training-environment/packages/container/training-environment-rstudio-test3-app/settings)
and use *Change visibility* to make it public. The build workflow warns while
it is private.

Then add this block to `ood_apps` in `vars/ondemand-config.yml` of the
[training-environment](https://github.com/nesi/training-environment) deployment:

```yaml
  rstudio_test3:
    k8s_container: ghcr.io/reannz-training-environment/training-environment-rstudio-test3-app:v0.1.0
    repo: https://github.com/reannz-training-environment/training-environment-rstudio-test3-app.git
    version: 'v0.1.0'
    enabled: true
    pre_pull: false
```

Set `pre_pull: true` while a workshop is using the app, so the image is cached
on every worker node before learners start sessions.

## Releasing a new version

A session runs the image tag that `submit.yml.erb` pins. Pushing a commit to
`main` that pins a new `v*` tag releases it: the *Release* workflow tags the
commit and starts the image build for that tag. Then update `k8s_container`
and `version` in the training-environment config to the new tag.

With the app creator, bump `version` in
[`apps/test3.yml`](https://github.com/reannz-training-environment/training-environment-app-creator/blob/main/apps/test3.yml),
and merge the update pull request it opens here.

Every push also builds an image tagged with the branch name. While developing,
pointing `submit.yml.erb` at a branch tag, with `image_pull_policy: Always`, makes
a restarted session pick up each new build.

## How a session works

* `form.yml`, `manifest.yml` - the launch form and the dashboard tile
* `submit.yml.erb` - the k8s pod: image, resources, home directory and LDAP mounts
* `template/before.sh.erb` - sets up the host, port and password Open OnDemand connects with
* `template/script.sh.erb` - starts the GPU emulator, then starts RStudio
* `view.html.erb` - the connect button
* `docker/` - the image; `docker/scripts/smoke-test.sh` checks every feature during the build

`.github/workflows/build_container.yml` checks that `form.yml` parses the way
Open OnDemand parses it, that the template scripts are executable, and that a
release tag matches `submit.yml.erb`, then builds the image and pushes it to
`ghcr.io`.
